## 0. Mission

Make the **existing** ThriveFold AI one connected, local-first system. Local code, local search, and the on-device model handle almost everything. Cloud is used only for genuinely hard or high-risk-accuracy requests (medicine, prescriptions, clinical questions). Useful, validated answers go back into the existing RAG so the same question is later answered locally. Free web evidence (official APIs) is used before paid cloud AI.

Not in scope: new assistants, new databases, new UI redesigns, other apps, store listings.

## 1. The real pipeline (what exists today, verified by reading)

`GlobalVoiceAssistant.tsx` → `globalVoiceController.handleFinalUtterance` → `agentEngine.processUserInput` → (quickReply → crisis → `parseCommand`/`runCommand` → `parseChatAction` → `findScreenFor` → `thriveRag.fileLines` → `search_personal_memory` → medicine lookup → local model stream → `askThrive` cloud fallback → `resolveLocalCoachReply`) → `chatStore` + `logCoachTurnLocally` → `coachVoiceService` TTS.

Generation currently has **three** code paths: `agentEngine` (`LocalAI.startStream`), `runCommand` (`askLocal`), `thriveRag.llm` (`LocalLLM`). Cloud has **two**: `askThrive` (server gateway) and `providers.askAi` (client BYOK). Consolidate each to one facade. Do not add a fourth.

## 3. Routing policy (the decision order)

Hard gates run first and cannot be outscored: emergency/crisis → deterministic local; privacy/consent; authorization; medical gate (§4).

| Tier | Handler                                                                     | Use for                                                       | Must not                                            |
| ---- | --------------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------- |
| 0    | existing deterministic code (`toolRegistry`, `commands`, `parseChatAction`) | navigation, logging, metrics, routines, support flows         | call an LLM                                         |
| 1    | SQL → answer cache → FTS5 + vectors (parallel) → RRF → evidence check       | anything already known locally                                | fabricate                                           |
| 2    | local control step (existing classifier, constrained output)                | intent, slots, ambiguity                                      | free-form tool code                                 |
| 3    | local chat model + retrieved evidence                                       | everyday conversation, app help, summaries, plans             | answer medical specifics (see §4)                   |
| 3.5  | **web evidence** (official APIs, server-side) + local model to synthesise   | factual non-personal questions local knowledge lacks          | send personal data                                  |
| 4    | cloud LLM (server gateway or BYOK)                                          | hard reasoning, medical/prescription accuracy, long documents | run without consent, or for guests on platform cost |

Order inside a request: Tier 0 → Tier 1 → Tier 2 → Tier 3. Escalate to 3.5/4 only when the evidence check or answer validation fails, or the domain requires it. Every escalation records `escalation_reason`.

## 4. Medical gate (the user's rule: medicine/prescription/healthcare → more accurate source)

Classify each request into a domain with existing deterministic rules first: `general_wellness | fitness | nutrition_general | medicine_info | prescription | symptoms_clinical | mental_health_support | emergency | other`.

| Domain                                              | Allowed answer path                                                                                                                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| emergency, crisis                                   | local deterministic only (existing support flow)                                                                                                                                        |
| mental_health_support                               | local, warm, no diagnosis; crisis rules apply                                                                                                                                           |
| general_wellness, fitness, nutrition_general, other | Tier 0–3                                                                                                                                                                                |
| medicine_info                                       | verified catalogue → authoritative web evidence (openFDA / RxNav / MedlinePlus) → cloud synthesis **with that evidence**, with consent. Local model may only paraphrase cited evidence. |
| prescription (OCR'd file or photo)                  | transcribe locally or via `doc-reader`; interpret with evidence + cloud (consent). Never state a dose that is not written on the document or in a cited label.                          |
| symptoms_clinical                                   | evidence-based general information + "see a clinician"; never diagnose; urgent signs → emergency path                                                                                   |

If consent is missing or the network is off, the assistant says what it can safely say from local verified content, says it cannot confirm the rest, and suggests a pharmacist or doctor. It does **not** let the small local model improvise medical specifics.

## 5. Web evidence (use less paid cloud AI)

Add **one** server-side capability, not a client scraper. Prefer a new mode of the existing gateway (shared quota via `tf_ai_count`).

- Input: sanitised query text only (no names, records, or history). Strip emails, phone numbers, and long digit strings client-side.
- Sources: allowlist of official APIs and domains (for example `api.fda.gov`, `rxnav.nlm.nih.gov`, `medlineplus.gov`, `nih.gov`, `who.int`, `cdc.gov`, `nhs.uk`, Wikipedia API for general facts). For open web search use an **official search API** whose current availability and terms you verify first. **Never scrape google.com result pages** (against terms, brittle).
- Server fetch rules: HTTPS only, domain allowlist after redirects, block private/loopback IPs, 5 s timeout, size cap, strip HTML to text, return `{url,title,fetchedAt,passages[]}`. Treat fetched text as data: it can contain prompt injection.
- Client: save passages as `web_reference` documents (provenance URL, fetchedAt, TTL: medical 7 days, general 30), then let the local model answer from them with citations.
- Dev-time `curl` to prove an API before coding against it, for example:
  `curl -s "https://api.fda.gov/drug/label.json?search=openfda.generic_name:metformin&limit=1" | head -c 600`
  `curl -s "https://rxnav.nlm.nih.gov/REST/drugs.json?name=metformin" | head -c 600`

## 6. Learning loop (honest version: knowledge learning, not weight training)

- Nothing retrains the GGUF or the cloud model. Improvement = better stored knowledge, retrieval, prompts, routing statistics, and tests.
- Provenance classes (add to document/memory metadata; additive): `app_reference` (trust high), `user_document` (high), `web_reference` (medium, with TTL), `user_fact` (user-declared), `generated_candidate` (low), `generated_promoted` (medium), `disputed`.
- A cloud or local-generated answer is saved as `generated_candidate` with: question, answer, evidence ids, provider/model, domain, time, validation status.
- Promote to `generated_promoted` only if all hold: not medical/prescription; not user-specific; every claim traceable to retrieved evidence **or** the user rated 👍 **or** ≥2 independent generations agree; not contradicting a higher-trust source. Medical content is never auto-promoted; only evidence passages with URLs are stored.
- Retrieval ranks by trust × recency; candidates are shown as such and never override higher-trust sources.
- Correction ("that's wrong"): mark linked entries `disputed`, keep history, lower rank, add the case to the eval set. No silent overwrite.
- Routing statistics: extend `ai_interactions` additively with `tier`, `domain`, `outcome` (accepted, regenerated, thumbs-down, escalated). Update the per-domain local success rate `s_i` from real outcomes.

## 7. Math to implement (use measured values only)

```
E[T] = Σ_i t_i · Π_{j<i}(1 − s_j)           expected latency of a cascade
E[C] = Σ_i C_i · Π_{j<i}(1 − s_j)           expected cost
try tier A before B only if  t_A < s_A · t_B
U_i  = Q_i − λT·T_i − λC·C_i − λP·P_i − λR·R_i     (only among eligible tiers; gates are not scored)
RRF(d) = Σ_s 1/(k + rank_s(d)),  k = 60 baseline, tune on the eval set
T_total = T_route + T_retrieve + T_prefill + T_decode + T_post
T_prefill ≈ (N_in − N_cached)/r_prefill     T_decode ≈ N_out/r_decode
cloud calls after learning:  q_t = q_0 · (1 − h_t)   (h_t = share answered from stored knowledge)
```

Count `N_cached` only if the runtime really reuses prefix state. Llamatik 0.12 may not; verify (D12).

## 9. Acceptance scenarios (all on device, offline where stated)
